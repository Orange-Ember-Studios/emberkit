# SSR & SSG

<Text color="muted" className="mb-6">EmberKit ships four rendering modes controlled by <code className="text-primary-400">emberkit.config.ts</code>. The Vite plugin handles SSR during development; the CLI builds client and server bundles and can pre-render static routes at build time.</Text>

### How routes are classified

During `emberkit build`, each file under `src/routes/` becomes a manifest entry:

- **Static route** — path has no dynamic segments (e.g. `/`, `/about`, `/docs/installation`)
- **Dynamic route** — path contains a segment parameter (e.g. `/blog/:slug` from `[slug].tsx`)

In **hybrid** mode, static routes are written to `dist/.../index.html` at build time. Dynamic routes are rendered at request time via `dist/server/entry-server.js`.

## Configuration

Create `emberkit.config.ts` in your project root (or run `emberkit generate config`):

```typescript
import { defineConfig } from '@emberkit/core';

export default defineConfig({
  mode: 'hybrid', // 'static' | 'ssr' | 'spa' | 'hybrid'
  server: {
    port: 3000,
    host: 'localhost',
  },
  build: {
    outDir: 'dist',
    target: 'esnext',
  },
  // Optional: merge extra Vite options
  vite: {
    plugins: [/* emberkitVitePlugin(), tailwindcss(), … */],
  },
});
```

Register the Vite plugin in `vite.config.ts` (included in CLI templates):

```typescript
import { defineConfig } from 'vite';
import { emberkitVitePlugin } from '@emberkit/core/vite-plugin';

export default defineConfig({
  plugins: [emberkitVitePlugin()],
  esbuild: {
    jsxImportSource: '@emberkit/core',
  },
});
```

The plugin reads `emberkit.config.ts` for `mode`, `routeDir`, markdown options, and compression. If no config file exists, **hybrid** is the default.

## Development

```bash
pnpm dev   # emberkit dev — Vite + HMR
```

For every mode except `spa`, the dev server runs SSR middleware on HTML navigations:

1. Skips assets, HMR, and non-HTML requests
2. Loads the virtual SSR entry and calls `render(url, server)`
3. Injects rendered markup into `index.html` at `#app` (or `<body id="app">`)

View the page source in the browser to confirm server-rendered HTML before hydration.

## Production Build

```bash
pnpm build   # emberkit build
```

| Mode | Steps |
|------|--------|
| `spa` | Client bundle → `dist/` |
| `ssr` | Client bundle → SSR bundle → `ssr-manifest.json` |
| `hybrid` | Client → SSR → manifest → pre-render **static** routes |
| `static` | Client → SSR → manifest → pre-render **all** non-dynamic routes |

Build artifacts:

```
dist/
├── index.html              # Client shell (and / for pre-rendered home)
├── assets/                 # JS, CSS, hashed chunks
├── ssr-manifest.json       # mode, routes[], isStatic flags
├── server/
│   └── entry-server.js     # SSR renderer (unless you provide src/entry-server.tsx)
└── about/
    └── index.html          # Pre-rendered static route (hybrid/static)
```

### Preview and production servers

```bash
pnpm preview   # emberkit preview — quick local check (default port 4173)
pnpm serve     # emberkit serve — production server using ssr-manifest.json
```

**Preview** serves static files and calls `entry-server.js` for SSR modes.

**Serve** resolves requests in order: static asset → pre-rendered `path/index.html` → SSR (for `ssr` mode, or dynamic routes in `hybrid`) → SPA fallback to root `index.html`.

<Alert variant="info" title="Custom server entry">
  Add <code>src/entry-server.ts</code> or <code>src/entry-server.tsx</code> to replace the generated SSR shim. Export <code>render(url)</code> returning <code>{'{ html, status }'}</code> or an HTML string.
</Alert>

## Route metadata (built-in SSR head)

The default server entry injects optional route exports into <code>{'<head>'}</code>:

```tsx
// src/routes/about.tsx
export const metadata = {
  title: 'About — My App',
  description: 'Learn more about us',
};

export default function AboutPage() {
  return <main><h1>About</h1></main>;
}
```

For declarative head tags from components, use the <code>{'<Head>'}</code> component — it updates the DOM on the client and registers tags during render. See [Head](/en/docs/head) for details.

## Custom error pages

Place these in `src/routes/` (not nested under a segment):

| File | When used |
|------|-----------|
| `404.tsx` | No route matches |
| `500.tsx` | Uncaught error while rendering a route |

If neither file exists, EmberKit renders built-in default pages (same components used for client navigation). Custom pages receive `pathname` on 404 and `error` on 500.

```tsx
// src/routes/404.tsx
export default function NotFound() {
  return (
    <main>
      <h1>404</h1>
      <p>Page not found</p>
    </main>
  );
}
```

## Dynamic route props

SSR passes `params` to the matched route component:

```tsx
// src/routes/blog/[slug].tsx
import type { RouteParams } from '@emberkit/core';

export default function Post({ params }: RouteParams<{ slug: string }>) {
  return <article><h1>{params.slug}</h1></article>;
}
```

On the client, the runtime also provides `params`, `query`, and `request` via `RouteParams`. See [Routing](/en/docs/routing).

## Low-level HTML APIs

These utilities live in `@emberkit/core` for custom servers and tests:

### renderToHTMLString

```typescript
import { renderToHTMLString } from '@emberkit/core';

const fragment = renderToHTMLString(<Page />);
// HTML fragment (body content only)
```

`renderToHTMLString` escapes text and string attributes for safe SSR output.

### Head registry

```typescript
import { drainHeadContent } from '@emberkit/core';

// After rendering components that use <Head>:
const headTags = drainHeadContent();
```

Use this in a custom `entry-server` when you need full `<Head>` support in SSR.

<Alert variant="warning" title="Internal helpers">
  <code>renderSSR</code>, <code>createHtmlDocument</code>, and <code>createStreamingRenderer</code> exist in the core package for advanced integrations but are not part of the public <code>@emberkit/core</code> export surface today. Prefer the CLI pipeline or <code>renderToHTMLString</code> + <code>drainHeadContent</code> for custom servers.
</Alert>

## Hydration after SSR

Server HTML includes `data-ek-bind` indices and `data-ekclick` handler ids for interactive regions. The client entry reconnects signals and events without re-rendering the full tree. Details: [Hydration](/en/docs/hydration).

## Performance (why speed is the goal)

EmberKit’s rendering modes exist to minimize time-to-content and client work:

| Technique | Speed benefit |
|-----------|----------------|
| SSR / pre-render | Users see HTML immediately; no empty shell waiting for JS |
| `static` / `hybrid` pre-render | Static paths served from disk or CDN — very low TTFB |
| Selective hydration | Smaller JS parse/execute; faster Time to Interactive on content-heavy pages |
| Signal DOM binding | Updates skip virtual DOM diffing — only bound nodes change |

Speed is the framework’s first principle; weight and zero-JS defaults support it. See [Introduction](/en/docs/introduction).

## Edge deployment

Deploy pre-rendered `dist/` to any static host, or run `entry-server.js` on Node, Bun, or edge adapters. See [Edge Deployment](/en/docs/edge).
